\section{General notes}
    \paragraph{}
    This report presents the development, implementation, and evaluation of several embedded control systems
	for the TurtleBot platform. Over four laboratory sessions, we progressively implemented I2C communication,
	sensor data handling, servo stabilization, PID motor speed control, and line-following navigation using 
	a custom yaw controller. Each lab builds upon the previous work and introduces increasingly complex real-time
	control tasks.

	\paragraph{}
	This report was created as part of the evaluation for the Embedded Real-Time Control course at UNIPD.
	All laboratory work and development were performed on a device named TurtleBot (see picture \ref{fig:turtlebot}).
	STM32 CUBE IDE was used as the software development tool.

	\paragraph{}
	We use a microcontroller from the STM32F7 series, part of STMicroelectronics' STM32 family, based on the ARM Cortex-M7 core, operating at frequencies up to 216 MHz. 
	It is designed for high-performance embedded applications that require substantial processing power combined with real-time capabilities. 
	The STM32F7 features up to 2 MB of dual-bank Flash memory, up to 512 KB of SRAM (with additional TCM memory), and includes an integrated 
	Floating Point Unit (FPU) and Digital Signal Processing (DSP) instructions for efficient signal processing tasks. Key peripherals include 
	high-speed USB OTG (with support for full-speed and high-speed modes), multiple 12-bit ADCs and DACs, timers with encoder and PWM modes,
	as well as extensive connectivity options such as UART, SPI, I²C, CAN, SDIO, and Ethernet MAC with IEEE 1588 support.
	The series also includes an L1 cache (I-cache and D-cache), Chrom-ART Accelerator for graphical applications, 
	and flexible memory interfaces for external SDRAM, SRAM, or NOR/NAND Flash.
	These features make the STM32F7 well-suited for applications involving advanced user interfaces, audio processing, motor control,
	and industrial automation.

\section{Laboratory 2}

        \item \textbf{Counter Period}: With the counter period of 100, we thus get the desired update frequency of $10kHz/101 \approx 100 Hz.$
    \end{enumerate}

    \subsection{IMU Data Handling}
    \paragraph{}
    The TurtleBot is equipped with a 6-DOF IMU, consisting of a 3-axis accelerometer and a 3-axis gyroscope. The accelerometer measures the linear acceleration (m/$s^2$) along the three axes, while the gyroscope measures angular velocity (rad/s) around these axes. The data from the two sensors is available via
    
    \verb|bno055_convert_double_accel_xyz_msq()| and \verb|bno055_convert_double_gyro_xyz_rps()|, respectively.  The data provided by the IMU is crucial when estimating the movement and orientation of the robot, particularly for calculating the tilt as follows:

    \begin{equation*}
        \theta = sin^{-1}(\frac{a_y}{g})
    \end{equation*}
    where $a_y$ is the acceleration along the y axis.

    \subsection{Servo Control}
    \paragraph{}
    The two servo motors controlling the movement are operated via PWM signals generated by TIM6 of the STM32, and the angles are updated with a frequency of 100 Hz using the \verb|__HAL_TIM_PeriodElapsedCallback| function and scaled into a safe duty cycle with the \verb|saturate()| function. 
    \begin{lstlisting}[language=C, caption={Angle update function}, label={lst.lab1.line} ]
    TIM_HandleTypeDef * timer6_ptr = &htim6;
    HAL_TIM_PeriodElapsedCallback(timer6_ptr)
    {
    theta = asin(d_accel_xyz.y/G); 
    pan = (int8_t)(-(theta/3.14)*180) + PAN_BIAS;

    angle = angle + ((-(d_gyro_xyz.z*0.1)/3.14)*180.)/10.;

    tilt = (int8_t)angle;
    }
    \end{lstlisting}
    As can be seen in the code, there is a strange phenomenon where dividing the angle update formula by 10 ensures a smooth pan without the need for a filter. While this does not make sense time/frequency-wise (after having done the calculations multiple times), it does in the end provide a very smooth movement. The most probable reason is that, by reducing the amplitude of the response, some noise from the gyroscope is actually "filtered".

        \subsection{Theoretical background}
            \paragraph{}
            	A DC motor changes its speed depending on the voltage we apply and the load it experiences. In order to keep the speed at a set value, we need a feedback controller designed to work properly even when conditions change.
            \begin{figure}[H]
				\centering
				\includegraphics[width=0.7\textwidth]{figures/system_model.png}
				\caption{System model}
				\label{fig:system_model}
            \end{figure}
            \paragraph{}
            The motor can be easily described by using two equations, one for the mechanical part and another for the electrical side, as follows:
            
            \textbf{Electrical:} From Kirchhoff’s Voltage Law (KVL) applied to the armature circuit
\begin{align}
    V_a(t) &= R_a i_a(t) + L_a \frac{di_a(t)}{dt} + V_b(t) \\
    &= R_a i_a(t) + L_a \frac{di_a(t)}{dt} + K_b \omega(t),
\end{align}

\textbf{Mechanical:} From Newton’s second law applied to the rotor
\begin{align}
    J \frac{d\omega(t)}{dt} &= T_m(t) - b \omega(t) \\
    &= K_t i_a(t) - b \omega(t),
\end{align}
where $V_a(t)$ is the armature voltage (input voltage) [V], 
$i_a(t)$ is the armature current [A], 
$R_a$ is the armature resistance [$\Omega$], 
$L_a$ is the armature inductance [H], 
$V_b(t)$ is the back EMF (Electromotive Force) [V], 
$K_b$ is the back EMF constant [V/(rad/s)], 
$\omega(t)$ is the angular velocity of the rotor [rad/s], 
$T_m(t)$ is the motor torque developed by the motor [Nm], 
$K_t$ is the torque constant [Nm/A], 
$J$ is the moment of inertia of rotor and load [kg$\cdot$m$^2$], 
and $b$ is the viscous friction coefficient (damping) [Nm/(rad/s)].

\paragraph{}
By using the Laplace transform and considering $K = K_t = K_b$, we get the motor's transfer function:

\begin{equation}
    G(s) = \frac{\Omega(s)}{V_a(s)} = \frac{K}{L_a J s^2 + (R_a J + L_a b)s + (R_a b + K^2)}
    \label{eq:full_tf}
\end{equation}

\paragraph{}
Considering the fact that the effects of the inductance are not significant compared to other time constants, the model can be simplified to a first-order approximation.

\paragraph{}
In our experiment, the transfer function used for tuning the controller had the form:

\begin{equation}
    P(s) = \frac{\mu}{1 + T s} \cdot e^{-\tau s}
    \label{eq:approx_tf}
\end{equation}

with $\mu = 3.552$, $T = 0.217$, $\tau = 0.2$. These values represent the system gain, time constant, and a small time delay.

\paragraph{}
The PWM (Pulse Width Modulation) signal allows us to adjust the motor speed by changing the voltage applied. In this way, the duty cycle varies, the voltage change is not done directly, and speed control is smooth.

\paragraph{}
The first thing we did was create a structure where we defined the PID controller's parameters. It consists of the proportional, integral, and derivative gain, error terms, and the output. It is important to note that we had to create two instances of this structure, one for the left wheel and one for the right wheel. 


\begin{lstlisting}[language=C, caption={PID calculation function}, breaklines=true]
void pidRecount(pid_attributes_t * pid_attributes, motor_attributes_t * motor_attributes)
{
	pid_attributes->error_previous = pid_attributes->error;
	pid_attributes->error =  motor_attributes->wheel_set_speed - motor_attributes->wheel_read_speed;

	pid_attributes->derivation = pid_attributes->error - pid_attributes->error_previous;

  if(( pid_attributes->integration +100 < 3000) && (pid_attributes->integration -100 > -3000))
    pid_attributes->integration += pid_attributes->error;

  double integral_part = (TS/pid_attributes->Ti)*pid_attributes->integration;
  
  double derivate_part = (pid_attributes->Td/TS)*pid_attributes->derivation;
  
  pid_attributes->output = pid_attributes->Kr*(pid_attributes->error + derivate_part + integral_part);

}

\end{lstlisting}

\paragraph{}
The function \textbf{pidRecount} computes the PID controller, which updates after each timer interrupt. The proportional, integral, and derivative gains for the controller were chosen by experimenting, which means different values were tested on the system until we obtained a satisfactory set of parameters. This set ensures good performance in terms of tracking the reference, as required in the task. Inside $HAL_TIM_PeriodElapsedCallback$, control operations such as PID calculation and PWM update are performed periodically.

        \subsection{Error definition}
            \paragraph{}
            For starters, let us define our yaw error:
            \begin{equation}
                \psi_{err} = \psi_{ref} - \psi
            \end{equation}
            
        \begin{figure}[H]
			\centering
			\includegraphics[width=0.4\textwidth]{figures/yaw_error.png}
			\caption{Yaw error definition}
			\label{fig.lab4.yaw_error}
		\end{figure}

        As shown in the picture, the error that the yaw controller receives is calculated as the difference between the reference and the current value. We want this error to be minimal.
        It is also possible to rewrite the equation stated above with respect to the error of following the line, namely ${e_{esl}}$.

        \begin{equation}
            \psi_{err} = arctan(\frac{e_{esl}}{H})
        \end{equation}
        where $H$ is the distance between the line sensor and the vehicle’s center, equal to 0.085 m, and $e_{esl}$ is defined as:

        \begin{equation}
    e_{esl} = 
    \begin{cases}
    0, & \text{when the line is at the center} \\
    > 0, & \text{when the line is on the left side of the sensor} \\
    < 0, & \text{when the line is on the right side of the sensor}
    \end{cases}
    \end{equation}

    Therefore, using basic mathematical knowledge, the arctan(x) is not needed when the value of x is close to 0 (zero). In conclusion, we can define the yaw error as follows:
    \begin{equation}
        \psi_{err} = \frac{e_{esl}}{H};
    \end{equation}

    We implemented the yaw error as follows:

    \begin{lstlisting}[language=C, caption={Yaw error}, label={lst.lab4.yaw_error} ]
    
  trurtle_bot->TB_jaw_error = (line_attributes->distance_from_center/LINE_SENSOR_DISTANCE);

    \end{lstlisting}

    \subsection{Yaw controller Design}

    For the design of the Yaw controller we implemented the following structure in Matlab Simulink:

    For the controller, namely $C_{\psi}$, it is multiplied by the error that we have defined above. Taking this into consideration, we defined the yaw controller by implementing a proportional (P) control. The value of the yaw controller is defined by the variable $K_r$.

    \begin{lstlisting}[language=C, caption={Yaw controller}, label={lst.lab4.yaw_controller} ]

    \end{lstlisting}

    With everything defined, we can introduce the Simulink model we implemented:

    \begin{figure}[H]
			\centering
			\includegraphics[width=1\textwidth]{figures/schema_sim.png}
			\caption{Simulink model}
			\label{fig.lab4.simulink}
		\end{figure}

    We can clearly see both the PIDs that are intended for controlling the speeds of both wheels. In the effort to find a suitable PID for both wheels such that the overall error is minimal, we implemented a metaheuristic method using the MATLAB function PSO.
    PSO stands for Particle Swarm Optimization, and it is a method in which we can find the parameters of both the PIDs and the yaw controller gain by running the simulation multiple times and placing particles throughout the search space.

    The particles have unique attributes, such as:
    \begin{enumerate}
        \item knowledge of their position in the search space
        \item knowledge of the swarm's position in the search space
        \item knowledge of their value
        \item knowledge of the swarm's values
    \end{enumerate}

    The goal of this metaheuristic is to find the global optimal value that satisfies the condition given by the user. The condition given is that we want the overall error to be minimal. This can be described as:
    \begin{equation}
        J = \| \psi_{error} \|;
    \end{equation}

    In this way, the goal of the algorithm is to move the particles in the search space at every iteration. Then, by running the simulation with the values obtained in that iteration, the particles obtain an output that is normalized for easier comparison. In the end, after multiple iterations, the particles should gather in a small area, which in the end is the global optimum value, namely the minimal error found in the designated search space.

    For the algorithm to work properly, we implemented different intervals that the values should take. Therefore, we can run the same algorithm with multiple choices, building multiple configurations.

    The preset configurations are :

This flowchart represents how the code works. We can further expand this chart by summarizing what each node does in particular. Taking this into consideration, we can define the starting points of the program as follows:
\begin{enumerate}
    \item \textbf{Start main()}: This node represents the program entry point. The function main() is called automatically when the controller starts.\
    \item \textbf{Initialization: Peripherals, Timers, UARTs, Motors, Sensors}: Here, all hardware peripherals are initialized.\
    \item \textbf{Set PID parameters and Initial Speed}: The PID controller constants ($K_r$, $T_i$, $T_d$) for both wheels and the yaw controller are set. The initial desired speed of the robot is also set.\
    \item \textbf{Main loop}: The main loop only updates the data logger.\
    \item \textbf{Log Data: $ertc^{dlog}_{update()}$}: Within the main loop, this function is called to update the state of the data logger, handling any data transmission or storage as needed.\
\end{enumerate}

After the main loop is triggered, the program enters two different interrupts: TIM6 and TIM7. We can define TIM6 as follows:
\begin{enumerate}
    \item \textbf{TIM6 Interrupt}: This node represents the TIM6 interrupt service routine (ISR), which is triggered periodically based on the timer’s configuration. It is used for periodic logging and status signaling.\
    \item \textbf{Prepare Data Log Packet}: The relevant control and sensor variables are packed into a data structure (struct datalog) for transmission or storage.\
    \item \textbf{Send Data via UART}: The prepared data log packet is transmitted over UART, allowing monitoring or recording of the robot’s behavior.
\end{enumerate}

For TIM7 we have the following:
\begin{enumerate}
    \item \textbf{TIM7 Interrupt}: This node is the TIM7 interrupt service routine, also triggered at a regular interval. It handles the core control logic and sensor updates for the robot.\
    \item \textbf{Read Line Sensors, Get Wheel Speeds}: The robot reads the line sensor values and gets the current wheel speeds.\
    \item \textbf{Sensor Accumulation and Oversampling}: Multiple readings from the line sensors are accumulated and processed (oversampling) to reduce noise and improve accuracy.\
    \item \textbf{Compute Distance from Center, Yaw error, Angular Velocity, PID Output}: The robot calculates how far it is from the center of the line, computes the yaw tracking error, estimates the robot’s angular velocity, and calculates the output of the yaw PID controller.\
    \item \textbf{Update Wheel Set Speeds}: Using the yaw PID output and the current speed setpoint, new set speeds are assigned to the left and right wheels to steer the robot appropriately.\
    \item \textbf{PID Recount}: Each wheel’s PID controller updates its output, based on the difference between the desired and measured wheel speeds.\
    \item \textbf{Update Motor PWM Duty Cycle}: The computed PID outputs are used to update the PWM signals sent to the motor drivers, controlling the actual speed of each wheel.
\end{enumerate}

In summary, this flowchart provides a clear overview of the software architecture, highlighting the separation of concerns between control and logging, and illustrating how periodic tasks are efficiently managed using timer-based interrupts in an embedded system context.
